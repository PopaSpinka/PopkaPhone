# Рентген телефона

`tools/xray` — запись всего, что делает система телефона, на несколько секунд или на весь прогон стола, и разбор:
кто сколько работал, на каких ядрах, сколько ждал своей очереди и за кем, что его блокировало. Сделан 19 ноября 2026
для разбора «сверху вниз» ([AUDIT.md](AUDIT.md)): прежние инструменты видели оболочку изнутри (зонд `/probe`,
`tools/deskbench`) и систему раз в четверть секунды (`device/desksampler.py`), а чужие процессы (Chromium, службы
Android, ядро), прерывания, сон ядер и ожидание ядра по каждому потоку — нет.

## Как устроено

Телефон только пишет — `device/xray.py` (от root; на телефоне — `~/naomi/bin/xray.py`), разбор — на Mac:

- **трасса ядра** (ftrace, `/sys/kernel/tracing`, часы `mono` — CLOCK_MONOTONIC, как у трассы стола и журнала
  оболочки `-o short-monotonic`): `sched_switch`, `sched_wakeup`, `sched_migrate_task`, `sched_blocked_reason`
  (сон в ядре не по своей воле: замок, диск, память — с функцией ядра), `irq_handler_*`, `softirq_*`,
  `cpu_frequency`, `cpu_frequency_limits`, `dcvsh_freq`, `cdev_update`, kgsl (`adreno_cmdbatch_queued/submitted/
  retired` — задания видеочипа по процессам, `kgsl_pwr_set_state`, `kgsl_pwrlevel`, `kgsl_buslevel`), буферы кодера
  (`msm_v4l2_vidc_buffer_event_*`); со словом `idle` — ещё `cpu_idle` (событий много). Буфер — 64 МБ на ядро на время
  записи (1,2 млн событий: на полный прогон стола, ~6 минут, хватает; с игрой Android — нет, см. «Грабли»), потом
  возвращается как был;
- **два снимка** `/proc` и `/sys` — до и после (`state.json`): все потоки (чей, имя, nice и класс, группа schedtune,
  разрешённые ядра, тики, `schedstat`), ядра (`/proc/stat`, `time_in_state`, счётчики и время состояний сна),
  прерывания и куда они разрешены, тепло и ограничители, мощность (кабель и батарея), видеочип, память (`meminfo`,
  `vmstat`, PSI, ION, kgsl по процессам; PSS по процессам — раз, после трассы), сеть и повторы TCP, диск.

Запись замер не искажает: одни и те же шаги стола с рентгеном и без него — путь кадра 25,0 / 25,4 / 24,8 / 25,1 мс
(по два прогона, 19 ноября 2026).

## Команды

```sh
tools/xray run [сек] [имя] [idle] [-- команда …]   # запись (10 с) и разбор → reports/xray-ДАТА-имя/report.txt;
                                                   # команда после «--» запускается на Mac через 1 с после начала
tools/xray again ПАПКА [слово …]                   # разобрать снова; слова — какие потоки считать главными
tools/xray step ПАПКА [шаг | С ПО]                 # отрезок записи: шаг сценария или секунды от начала
tools/xray thread ПАПКА СЛОВО                      # один поток: куски работы, где ждал, за кем, кто будил, блокировки
tools/xray compare A B                             # две записи: ядра, главные потоки, ожидания
tools/xray trap [сек] [-- команда …]               # «ловушка»: где поток интерфейса оболочки засыпает не по своей воле
tools/xray disk [сек] [-- команда …]               # задержка диска «со стороны стола»

DESKBENCH_XRAY=1 tools/deskbench run [шаг …]       # прогон стола с рентгеном: xray/ в папке прогона,
                                                   # report.txt — весь прогон, report-ШАГ.txt — каждый шаг
```

С `DESKBENCH_XRAY=1` прогон стола «чистый»: выборки стека выключены (вернуть — `DESKBENCH_SAMPLE=1`), сборщик — раз в
секунду и без процессов (их до потока видит трасса). Причина — в «Что рентген показал про сами замеры».

**Ловушка** (`device/uitrap.sh`) — отдельная запись ftrace (`instances/naomi_trap`) только одного потока — потока
интерфейса оболочки: его `sched_switch` и стек ядра всякий раз, когда он засыпает не по своей воле (состояние D: диск,
замок, память), плюс причина (`sched_blocked_reason`). Событий — сотни в секунду: не переполняется, работе не мешает,
с рентгеном не спорит. Итог — сводка «причина ← цепочка функций ядра: раз, всего мс, худший» и самые долгие засыпания
с секундой по часам телефона (те же часы, что в трассе стола `desk.csv`, — долгое событие стола находится по времени);
сырая запись — `reports/trap-ДАТА.txt`. Так 20 ноября 2026 найдены открытие файла посреди кадра (72 мс за чтением
каталога) и ожидание карты памяти процесса по 40–60 мс, пока другой поток оболочки делает `fork` (запуск `pactl`).

**Диск** (`device/ioprobe.py`) — раз в 20 мс читает 4 КБ мимо кэша (`O_DIRECT`) из случайного места образа системы
Android (2,9 ГБ, `/userdata`) и считает, сколько ждал: середина, 95 %, 99 %, худшее. В покое — 1,5 мс (диск успевает
уснуть), под нагрузкой с `noop` — 0,3 мс; с прежним `cfq` под загрузку игры — 95 % проб до 61 мс.

Без команды обе работают заданное число секунд (30), с командой после `--` — пока она идёт
(`tools/xray disk -- tools/deskbench run android-cold`).

## Как читать отчёт

- **ЯДРА** — занятость по трассе, доля прерываний, смены частоты, доли состояний сна (C0 — мелкий, C1/C2 — глубокий),
  частоты по времени, группы schedtune.
- **ПРОЦЕССЫ / ПОТОКИ** — время на ядрах; «мал / бол / гл» — доля на малых A55, большом A76 (ядро 6) и главном A76
  (ядро 7); класс — nice или FIFO/RR; **ожидание** — от пробуждения до ядра (медиана / 95 % / худшее); **вытеснен** —
  был готов работать, а ядро отняли; **блок** — сон в ядре не по своей воле.
- **КТО ОТНИМАЛ ЯДРО У ГЛАВНЫХ ПОТОКОВ** и **ХУДШИЕ ОЖИДАНИЯ** — для потоков, от которых зависит плавность (список
  слов — `FOCUS` в `tools/xray`): сколько ждал и за кем. «За: ядро просыпалось» — ядро было свободно, но спало:
  ожидание — это выход из сна.
- **ЧТО БЛОКИРОВАЛО** — функция ядра, раз, всего, худший.
- **ПРЕРЫВАНИЯ** — по времени обработчика, на каких ядрах были и куда разрешены; отложенные (softirq).
- **ВИДЕОЧИП** — состояния (ACTIVE / SLUMBER), смены уровня, задания и занятость по процессам.
- **ТЕПЛО, ПАМЯТЬ, СЕТЬ И ДИСК** — по снимкам: самые горячие зоны, включённые ограничители, PSS по программам, отказы
  страниц, скорость по интерфейсам, повторы TCP.
- **Сверка** — занято по трассе против тиков `/proc` (расходится на потоки, родившиеся и умершие за запись).

Для отрезка (шаг сценария) в отчёте только то, что из трассы: снимки сняты по краям всей записи.

## Что рентген показал про сами замеры

Первый же прогон (19 ноября 2026) показал, что `tools/deskbench` мерил не совсем то, что видит пользователь:

- **выборки стека** (1 кГц, SIGPROF потоку интерфейса) не давали главному ядру уснуть — и прятали главную задержку
  пути кадра, выход ядер из глубокого сна ([AUDIT.md](AUDIT.md), находка 1): с выборками такт доходил до потока
  интерфейса за 1,3 мс, без них (как у пользователя) — за 4,0;
- **сборщик** (`desksampler.py`, 4 раза в секунду, все процессы раз в секунду) — 9 % малого ядра;
- **тишина опросом** (`pactl` раз в 0,5 с) будила PulseAudio и шину: на каждое новое подключение к шине просыпаются
  `systemd`, `systemd-logind`, `polkitd`, `accounts-daemon`, `urfkilld`, `udisksd` — вместе ~4 % ядра. Теперь тишина —
  по событию нового потока (`pactl subscribe`).

Поэтому сравнивать числа прогонов до и после 19 ноября 2026 15:00 напрямую нельзя: прежние прогоны (с выборками) —
«как с запретом сна ядер».

## Чёрный ящик

Рентген — на секунды и минуты. То, что портит телефон за часы и дни (растёт память, копятся потоки и открытые файлы,
перезапускаются службы, перегрев), видно только на длинной записи, а журнал systemd у нас в памяти и перезагрузку не
переживает. Поэтому — служба `naomi-blackbox` (`device/blackbox.py`, ставит `tools/naomi install`): раз в минуту строка
JSON в `/userdata/naomi/blackbox/ГГГГММДД.jsonl`, хранится 14 дней, одна запись — ~30 мс процессора.

В строке: время и время работы (меньше прошлого — была перезагрузка), память (доступно, кэш, ядро, ION), занятость
малых и больших ядер за минуту, мощность от кабеля и ток батареи, датчики тепла и включённые ограничители, держат ли
«стол на полную», байты `usb0` и `wlan0`, место на `/userdata`; по процессам — оболочка, `naomid`, браузер (все его
процессы вместе), PulseAudio, `sshd`: pid (сменился — перезапуск), RSS, потоков, тики; у оболочки и браузера — ещё
открытых файлов, сокетов и dma-buf, у оболочки — потоков захвата звука.

```sh
tools/naomi blackbox [часов]    # что было за последние часы (24): перезагрузки, перезапуски, что растёт, тепло, мощность
```

Разбор смотрит последний непрерывный отрезок каждого процесса (тот же pid) и помечает «РАСТЁТ», если медиана второй
половины отрезка больше первой на 15 %: так нашлись бы обе утечки 19 ноября 2026 (захват звука — потоки, ролик
«Просмотра» — сокеты и память), не будь они найдены рентгеном.

## Грабли

- **Буфер трассы переполняется — отчёт врёт молча.** Буфер не перезаписывается (начало привязано к снимку «до»):
  кончился — ядро молчит до конца записи, и потоков на нём с этого места не видно: «работал на большом ядре»
  превращается в «ждал», доля малых ядер растёт. Игра Android (Unity: главный поток и помощники будят друг друга)
  даёт на большом ядре ~30 тысяч событий в секунду против 1–3 тысяч у стола — 64 МБ кончаются за 40 секунд. Так
  19–20 ноября 2026 получились ложные «поток интерфейса на 80 % на малых ядрах» и «ждёт ядро за игрой до 98 мс»
  (во всех прогонах с игрой дольше минуты терялись события ядер 6–7, до 2,8 млн). Теперь отчёт пишет «ВНИМАНИЕ:
  буфер трассы переполнился…» с ядром и секундой, с которой оно молчит, и «ЭТОМУ ОТЧЁТУ НЕ ВЕРИТЬ», если молчание
  задело отрезок; прогон стола повторяет это в своём выводе («РЕНТГЕН ШАГА … НЕВЕРЕН»). С игрой — запись до 30 секунд
  или шаг первым в прогоне.
- **Рентген сам мешает.** Буферы — 512 МБ памяти на время записи, каждое событие стоит времени ядра. Загрузка игры
  под перетаскивание окна, 20 ноября 2026: без рентгена задержек потока интерфейса (события от 4 мс) — 323 на
  1,8 с, пропусков монитора 8+3; с рентгеном — 963 на 5,4 с и 21+3. Числа «сколько кадров потеряно» брать из прогона
  без рентгена (`DESKBENCH_SAMPLE=0` без `DESKBENCH_XRAY`), рентген — чтобы понять, кто виноват.
- **Выборки стека роняли оболочку** (прогон без рентгена, `DESKBENCH_SAMPLE`). Обработчик выборок разбирает стек
  потока интерфейса (`backtrace`) там, где его застал сигнал, — и внутри драйвера видеочипа (библиотеки Android через
  libhybris), где таблицы раскрутки верны не в каждой точке: libgcc читал мусор — SIGSEGV. 20 ноября 2026 — два
  падения за два прогона (развёрнутая игра). Теперь разбор под охраной: упал — выборка пустая, оболочка цела
  (`naomiCrashJump`, `shell/app/unix_signals.*`; проверено: минута выборок при развёрнутой игре, 51 тысяча выборок).
- **Падение оболочки, программы стола или `naomid`** пишет в журнал стек упавшего потока («падение, стек потока:» —
  адреса и имена; своя функция без имени — `naomi-shell(+0x…)`: строку даёт `addr2line -Cfe naomi-shell 0x…` в среде
  сборки) и падает дальше как обычно — systemd перезапускает.
- **Перезапуск оболочки посреди прогона ронял её на выходе.** Прогон стола держит выборки стека весь прогон; 20 ноября
  2026 оболочку перезапустили (`tools/naomi run`) через 10 с после того, как другая сессия начала прогон, — «terminate
  called without an active exception», SIGSEGV, `naomi-safe`, и первый `tools/naomi run` после этого не вышел. Поток
  выборок (`samplerLoop`, `shell/app/desk_probe.cpp`) никто не останавливал: при разборе статических объектов он писал в
  уже освобождённый вектор выборок (SIGSEGV в `memcpy`), а его `std::thread`, ещё joinable, звал `std::terminate`.
  Воспроизводится наверняка: `Sample(файл)` и `tools/naomi run`. Теперь выборки останавливает выход оболочки
  (`aboutToQuit`; при `exit()` — деструктор), без файла — строка в журнале «выборки стека: прерваны выходом оболочки».
  Проверено 20 ноября 2026: старая сборка упала с первой попытки; исправленная — 18 перезапусков (8 подряд через ~2 с
  после старта; 8 — с идущими выборками, в том числе через 0,5 и 1 с после старта и один — с открытым браузером стола;
  2 — через 5 и 15 с; зритель на Pi), все — «Deactivated successfully», `naomi-safe` не включался. Ветка «деструктор при
  `exit()`» отдельно не проверена (оболочка так не выходит). Остальные потоки оболочки на выходе: кодер трансляции,
  «Файлы», яркость, скриншот стола, таймер кадров — ждут свой поток в деструкторе; захват звука не дождался за 0,3 с —
  отпускает поток, но всё, что поток трогает, у него в своих `shared_ptr`. Отпущенные сразу: закрепление кода (спит,
  трогает только libc), разбор видео «Просмотра» (свой объект GStreamer) и снимок `tools/naomi shot` — он ~2 с жмёт PNG
  средствами Qt, выход в эти 2 с не проверен.
- **`addr2line` — только по той сборке, что упала.** Сборку пересобирают за минуты (общая `~/naomi/build`), и адреса
  из старого журнала по новой сборке дают чужую функцию. Ту сборку можно собрать заново рядом: объекты, что с тех пор
  не пересобирались, — те же (время файлов `.o`), изменённые — из исходников той поры (`git show`), и тот же порядок
  сборки (`ninja -t commands app/naomi-shell`); сверка — адрес возврата из `backtrace` в `onCrash` (первая строка
  стека) должен совпасть.

- Рентгену нужен root (`sudo -n`), трасса — одна на систему: два рентгена сразу нельзя; `tools/naomi panel` и
  `hwtest` (vblank) тоже берут ftrace.
- Класс потока (nice) — из снимка «после»: прогон стола к этому моменту уже отключил зрителя, и поток интерфейса
  оболочки показан с nice 0, хотя весь прогон шёл с −5.
- Имя процесса служб Android — имя программы из `cmdline` (главный поток у них `binder:N_2`, `main`).
- `kworker` показывает, чем занят сейчас (`kworker/u16:0-governor_msm_adreno_tz`), — это имя на момент события.
- Регулятор частоты видеочипа сменить нельзя (`echo performance > …/devfreq/governor` — I/O error): опыт «без
  регулятора» не поставить.
